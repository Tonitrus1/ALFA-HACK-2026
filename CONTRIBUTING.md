# Работа в команде

## Начало работы

После принятия приглашения скачайте репозиторий:

```sh
git clone https://github.com/Tonitrus1/ALFA-HACK-2026.git
cd ALFA-HACK-2026
```

Для приватного репозитория потребуется авторизация в своём GitHub-аккаунте. Пароли и токены в команды и файлы проекта не вставляйте.

Перед каждой новой задачей обновляйте `main` и создавайте ветку:

```sh
git switch main
git pull --ff-only origin main
git switch -c frontend/login
```

Используйте префиксы `frontend/`, `backend/`, `ml/`, `docs/`, `fix/` или `integration/` и короткое название задачи. Постоянных веток frontend/backend/ml и develop нет. Не начинайте другую задачу в ветке уже завершённого Pull Request.

## Изменения и проверка

1. Внесите изменения в своей ветке. Делайте небольшие осмысленные коммиты, например `feat(frontend): add login screen` или `docs(architecture): clarify scoring input`.
2. Выполните проверки, подходящие для изменённой части. Пока кода приложения нет, проверьте документы, ссылки и примеры. Не указывайте непроведённые проверки как выполненные.
3. Отправьте ветку: `git push -u origin frontend/login`.
4. Откройте Pull Request в `main`, заполните шаблон и назначьте другого участника на проверку.
5. После одобрения хотя бы одним другим участником и разрешения всех обсуждений объедините изменения через Squash and merge. Удалите завершённую ветку.

Автор не одобряет собственный Pull Request. Прямая запись в `main`, принудительная перезапись `main` и удаление `main` запрещены командным регламентом. Первичная загрузка структуры репозитория выполняется владельцем до начала командной разработки.

При первоначальной настройке GitHub отказал во включении защиты `main` для этого приватного репозитория и указал на необходимость GitHub Pro. Поэтому сейчас эти правила остаются договорённостью команды, а не техническим ограничением доступа. Приватность сохранена, платный тариф не подключался. Если возможность защиты появится, включите одно обязательное одобрение другого участника, разрешение всех обсуждений и запрет принудительной перезаписи и удаления `main`.

Если нужно обновить уже начатую задачу, получите изменения через `git fetch origin` и объедините `origin/main` со своей веткой. Разрешите конфликты вручную и повторите профильные проверки. Не переписывайте чужие ветки.

## Общие интерфейсы и документация

Согласовывайте изменения API и форматов данных отдельным Pull Request до обновления потребителей. На этом этапе источник контрактов — `docs/architecture/contracts/`; копии в `packages/*/api/` внутри архитектурного комплекта генерируются.

Для изменений контрактов, миграций, общих настроек и безопасности запрашивайте проверку ответственного за направление и интеграцию. Реальные владельцы будут записаны в `.github/CODEOWNERS` после распределения ролей и предоставления доступа; файл с вымышленными логинами не создаётся.

Начните чтение архитектуры с [оглавления](docs/architecture/README.md). Правила изменения и пересборки комплекта приведены там же. Генераторы запускаются из `docs/architecture/` и изменяют файлы комплекта, а не корневой README проекта. После изменения документов обновляйте связанные представления и отчёты по инструкции комплекта; не переносите старые результаты проверки на новую редакцию.

Не коммитьте `.env` с рабочими значениями, токены, пользовательские документы, дампы баз, датасеты, веса моделей, зависимости и локальные кеши. Примеры конфигурации должны содержать только безопасные значения. Если секрет попал в историю, сначала отзовите и замените его.
