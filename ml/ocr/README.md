# OCR → LLM → Structured JSON

Самостоятельный внутренний Python 3.12 / FastAPI сервис для CPU. Принимает PDF,
PNG, JPEG и многостраничный TIFF, распознаёт каждый растр PaddleOCR с кириллической
моделью либо Tesseract rus+eng, вызывает внешний OpenAI-совместимый API и проверяет
ответ по JSON Schema и ссылкам на OCR-блоки. После реального сравнения Tesseract
выбран по умолчанию для чистых документов: он быстрее и точнее на включённом
наборе. `OCR_ENGINE=paddle` включает основной исследованный кандидат, который
оказался лучше на небольшом повороте скана. Это вывод по малому набору, не
универсальный рейтинг движков.
Текстовый слой PDF не используется как обход OCR.

Результат — **предложение для проверки пользователем**, не подтверждённая анкета,
не скоринг и не решение о кредите. Frontend/backend, загрузки CLEAN/AV, права
компаний, objectVersion и подтверждение финансовых значений подключаются отдельно.
Общий публичный API проекта не изменён. Сервис не принимает URL и не скачивает
переданные пользователями внешние ресурсы.

## Запуск

Обычный x86-64 ПК, Docker Engine/Compose, 4 CPU и ориентировочно 4 ГБ свободной RAM
для контейнера. Первая сборка скачивает Python-пакеты и открытые OCR-веса; сеть
также нужна внешнему LLM. GPU не нужен.

```powershell
cd C:\projects\ALFA-HACK-2026\ml\ocr
Copy-Item .env.example .env
# Заполните OCR_API_KEY случайным токеном, LLM_API_KEY ключом провайдера.
docker compose up --build -d
docker compose ps
```

Порт: `http://127.0.0.1:8001`. Swagger: `/docs`, OpenAPI: `/openapi.json`.
В Swagger нажмите Authorize и введите OCR_API_KEY. Ключ LLM передаётся только
сервису через окружение. `.env`, задания, документы, сырой OCR, кеши и веса
исключены из Git и build context. Не передавайте ключ в query string.

При пустом OCR_API_KEY приложение отказывается запускаться. `/health/live` проверяет
процесс; `/health/ready` — загрузку OCR, worker и наличие LLM-ключа, **не доступность
или баланс провайдера**. Неверный ключ провайдера выявляется реальным заданием.

## API

Все `/v1/*` требуют `X-API-Key`. Это общий токен доверенного backend, не IAM
для конечных пользователей. Прямой доступ браузера не предусматривается.

| Метод | Путь | Результат |
|---|---|---|
| POST | `/v1/jobs` | Multipart `files` (повторяется), HTTP 202 + job_id |
| GET | `/v1/jobs/{job_id}` | Статус, этап, метаданные файлов, TTL, безопасный error_code |
| GET | `/v1/jobs/{job_id}/schema` | Snapshot схемы именно этого задания, включая старые результаты |
| GET | `/v1/jobs/{job_id}/ocr` | Реальные блоки OCR: text, bbox, confidence, document_id/page/block_id |
| GET | `/v1/jobs/{job_id}/result` | Проверенный JSON, provenance, requires_confirmation=true |
| DELETE | `/v1/jobs/{job_id}` | Удаление документов, OCR и результата, HTTP 204 |
| GET | `/v1/schema` | Действующая JSON Schema извлечения |

Пример (bash, ключ сервиса уже в переменной окружения):

```sh
curl -H "X-API-Key: $OCR_API_KEY" \
  -F files=@passport.png -F files=@statement.pdf http://localhost:8001/v1/jobs
curl -H "X-API-Key: $OCR_API_KEY" http://localhost:8001/v1/jobs/JOB_ID
curl -H "X-API-Key: $OCR_API_KEY" http://localhost:8001/v1/jobs/JOB_ID/result
```

Полные примеры: `requests/ocr.http`, Postman collection, сохранённый `openapi.json`.
Имена пользователей/файлов не сохраняются: documents возвращаются в порядке
загрузки и содержат generated document_id, SHA256, content-sniffed media_type,
число страниц. Интегратор хранит соответствие с objectVersion на своей стороне.
Повтор POST создаёт новое задание; идемпотентность транспортного запроса — следующий
этап интеграции. Тайм-аут запроса не отменяет уже принятое задание.

Лимиты: 1–10 файлов, суммарно 50 страниц, 20 MiB/файл, 100 MiB/пакет,
20 ожидающих/обрабатываемых пакетов по умолчанию. Тип проверяется декодером,
а не расширением. Зашифрованные, пустые, повреждённые PDF отклоняются; растр —
не более 20 млн пикселей, PDF проверяется для максимальных 200 dpi. Пустой скан
даёт `OCR_NO_TEXT`. Некорректные файлы/пакеты отклоняются целиком.

Ошибки HTTP: 401 auth, 404 неизвестное/истёкшее задание, 409 результат ещё не готов,
413 размер/страницы, 415 формат, 422 файл/контракт, 429 очередь, 503 OCR не готов.
Ошибка асинхронного конвейера хранится в job.error_code, исходные исключения
и тела ответа провайдера не выдаются. `LLM_SCHEMA_INVALID`, `LLM_SOURCE_INVALID`,
`LLM_CONFLICT_INVALID`, `LLM_CONTEXT_LIMIT`, `LLM_INCOMPLETE_RESPONSE`,
`LLM_UNAUTHORIZED`, `LLM_RATE_LIMITED`, `LLM_TIMEOUT` не подменяются успехом.
После ошибки LLM распознанный текст остаётся доступен до TTL.

## Контракт и настройка

`schemas/extraction.schema.json` — источник контракта; `prompts/extract.txt` —
отдельный промпт. Их можно менять без изменения OCR/HTTP/worker. После изменения
перезапустите сервис. Новое задание сохраняет snapshot контракта и его SHA256;
восстановленное после сбоя использует именно этот snapshot.
Схему исторического результата нужно брать из `/v1/jobs/{id}/schema`, а не из
изменяемого `/v1/schema`. Соглашения корневых
`documents` и источников фиксированы валидатором. Удалённые `$ref` запрещены.
Для правок стандартной схемы также есть `scripts/build_schema.py`.

Общие секции: person (ФИО, дата рождения, ИНН, СНИЛС, паспорт), organization
(название, ИНН, КПП, ОГРН), financial (8 показателей, период, валюта), extensions.
Значения передаются строками: идентификаторы сохраняют ведущие нули, деньги —
десятичные **рубли**, даты — YYYY-MM-DD, период — YYYY либо ISO-интервал
YYYY-MM-DD/YYYY-MM-DD. Для интеграции с frontend нужны
преобразование в строки копеек и сопоставление snake_case/camelCase.

Каждое поле имеет status, value, confidence, sources, candidates:

- `extracted`: строковое значение и хотя бы один источник;
- `missing`: value/confidence=null, пустые sources/candidates;
- `conflict`: value/confidence=null, не менее двух различных candidates с источниками.

Источники ссылаются на document_id/page/block_id с точной непустой цитатой.
Проверяется существование блока и вхождение цитаты. Такая проверка предотвращает
несуществующие ссылки, но сама по себе **не доказывает, что значение семантически
следует из цитаты**. Качество извлечения проверяется отдельно по синтетическому
эталону. Confidence модели не калиброван, не является вероятностью истинности.
Контрольные суммы ИНН/СНИЛС, подлинность паспорта и банковских данных не проверяются.

Переменные окружения приведены в `.env.example`; дополнительно:
`CPU_THREADS=4`, `PAGE_DPI=150`, `MAX_QUEUED_JOBS=20`, `MAX_LLM_CALLS=32` на пакет.
MKL-DNN включён после реального CPU-прогона; `OCR_ENABLE_MKLDNN=false` отключает
ускорение при несовместимости конкретного CPU/runtime.
`LLM_RESPONSE_FORMAT=json_object` совместим с AITUNNEL; json_schema доступен для
провайдеров, поддерживающих данную схему. Независимо от режима локальная проверка
обязательна. Для провайдеров без расширений AITUNNEL установите
`LLM_REASONING_OPTIONS=false`. Каждый документ извлекается отдельно: модель не
может выбрать «более новый» отчёт и потерять противоречие. Большой документ
разбивается по страницам/блокам на контексты не более
MAX_CONTEXT_CHARS, каждый ответ отдельно проверяется, поля объединяются с
сохранением источников: различные строковые значения превращаются в conflict,
missing не затирает найденное. Лексически различные записи одного значения также
могут дать conflict: это консервативное поведение. Различная классификация страниц
одного документа даёт тип other. Один чрезмерно длинный блок или схема, не
помещающиеся в контекст, дают LLM_CONTEXT_LIMIT. Лимит задаётся в символах и должен
быть выбран с запасом под token window провайдера. Несколько вызовов увеличивают
стоимость/время и не заменяют проверку, что показатели относятся к одному периоду.
При ошибке схемы/ссылок допускается один настоящий запрос исправления JSON
(`LLM_VALIDATION_RETRIES=1`, можно 0): провайдер получает предыдущий ответ и
только пути/правила схемы, без сохранения невалидного ответа в файлы или логи.
Повтор тоже проверяется; провайдерские ошибки/429 не повторяются автоматически.
Исправления входят в лимит вызовов, usage и provenance.validation_repairs.

## Хранение и эксплуатация

SQLite хранит очередь и метаданные; отдельные каталоги — файлы, snapshot, OCR,
результат. Docker volume сохраняется при restart/down. Срок — 24 часа **с момента
приёма**, включая время обработки; логический доступ закрывается немедленно по
истечении, физическая очистка работает раз в 30 секунд. Пока сервис выключен,
очистка невозможна и выполняется при следующем запуске. Бэкапы volume не удаляются
сервисом. При штатном удалении результат работающего задания не публикуется.
TTL относится к локальному хранилищу; хранение данных на стороне внешнего LLM
определяется условиями провайдера.

Один CPU-worker, один процесс Uvicorn и один владелец volume (OS file lock).
Очередь восстанавливается при рестарте: processing → queued. Повтор после сбоя
может повторно вызвать платный LLM; exactly-once оплаты не гарантируется.
Горизонтальное масштабирование требует отдельной очереди/lease и object storage.
Очистка TTL работает отдельным потоком и не ждёт медленного LLM.
Нативный OCR не имеет жёсткого kill-timeout; ресурсы ограничены контейнером,
лимитами входных файлов и последовательной обработкой.

Порт привязан к localhost; для удалённого запуска требуются TLS, IAM/tenant
изоляция и ingress-лимиты. Локальный volume содержит чувствительные документы:
шифрование диска и защита Docker host — обязанность окружения. AV/quarantine —
за пределами модуля, принимать следует уже проверенные backend файлы.
Сервис не пишет тела документов, ключи, reasoning или ответы LLM в логи.

## Проверки

```sh
docker compose exec ocr pytest -q
docker compose exec ocr ruff check .
docker compose exec ocr python scripts/generate_fixtures.py
# Для Postman/HTTP-файла/curl с хоста скопировать только synthetic fixtures:
docker compose cp ocr:/app/fixtures .
docker compose exec ocr python scripts/benchmark_ocr.py
# Реальный платный запрос: только синтетические документы, два пакета.
# По документу на вызов: штатно 6 + 7 LLM-вызовов, исправления считаются отдельно.
docker compose exec ocr python scripts/verify_runtime.py
docker compose restart ocr
```

`pytest` проверяет контракт, загрузки и хранение; worker в HTTP-тестах явно
заменён и не является доказательством работы модели. `benchmark_ocr.py` запускает
настоящие PaddleOCR и Tesseract и измеряет CER/WER независимо от LLM.
`verify_runtime.py` проходит настоящий HTTP → OCR → LLM, отдельно проверяет схему,
источники, точные значения, отсутствующие поля и конфликт выручки.
Отчёт: `reports/verification.md`, машинные метрики рядом. Синтетические документы
генерируются локально и не включаются в Git; сохранены только генератор/метрики.

## Граница текущего этапа

Внешний API выбран пользователем как этап разработки. ТЗ компании требует
бесплатной проверяемой версии и LLM с открытыми весами: текущий внешний платный
endpoint не закрывает этот критерий. Следующий этап — локальная открытая модель
с тем же OpenAI API, проверка качества/контекста/памяти, offline-запуск.
Модуль не заявляет готовность всего кредитного конвейера к приёмке.
