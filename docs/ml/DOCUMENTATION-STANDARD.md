Общий формат объединяет эти свойства.

## 3. Рекомендуемая структура

Документация хранится централизованно в `docs/ml/`. Так её можно унифицировать без перемещения Python-кода, migrations, моделей и runtime OpenAPI.

```text
ml/
  README.md                       # каталог трёх сервисов
  scoring/README.md               # короткий вход в скоринг
  feed/README.md                  # короткий вход в рекомендации
  assistant/README.md             # короткий вход в ассистента
docs/ml/
  README.md                       # навигация по документации и её правила
  scoring/
    setup.md
    architecture.md
    integration.md
    model-card.md
    data.md
    operations.md
    verification.md
    THIRD_PARTY_NOTICES.md
    CHANGELOG.md
  feed/                           # тот же набор документов
  assistant/                      # тот же набор документов
```

`openapi.json`, `examples/`, `requests/`, `reports/`, `artifacts/` остаются по существующим путям. Документы ссылаются на них относительными ссылками. Одинаковое имя папки с примерами не является условием единого оформления. Для отсутствующей возможности писать «Не реализовано» или «Не применимо: причина», а не создавать фиктивный файл или команду.

`ml/README.md` становится каталогом, а не основной инструкцией скоринга. Общая архитектура `docs/architecture/` сохраняет свою роль. Сервисные документы объясняют конкретную реализацию и ссылаются на неё, не копируя большой архитектурный комплект.

## 4. Общее оформление

- Основной язык — русский; имена полей, статусы, команды и идентификаторы сохраняются как в коде.
- Один заголовок H1 на документ. Разделы H2/H3, без ручной нумерации заголовков. Порядок разделов берётся из шаблонов ниже.
- В начале: назначение, статус, дата актуальности, исходная ветка и commit проверенного снимка, проверенная среда. Для будущего шаблона незаполненные поля обозначаются явно.
- Статус реализации и результат проверки — разные поля. «Реализовано» не означает «проверено в Docker» или «принято командой».
- Перед каждым блоком команд указать ОС/оболочку и рабочий каталог. Shell и PowerShell показывать отдельными подписанными блоками. Не называть платформу поддержанной без фактической проверки.
- Для команд давать ожидаемый результат и способ проверить успех. Обозначать подготовку с сетью, обычный runtime, внешние платные вызовы и операции, изменяющие данные.
- Конфигурация оформляется таблицей: переменная, назначение, обязательность, значение по умолчанию, секретность. Примеры не содержат рабочих секретов.
- Документ описывает текущее поведение. История аудитов и изменений уходит в CHANGELOG и отчёты; README не наращивается хронологическими дополнениями.
- Все утверждения о метриках сопровождаются ссылкой на отчёт, версию модели и данные. Исторический отчёт явно помечается историческим.
- Сгенерированные OpenAPI, manifests и отчёты не переписываются вручную ради одинакового вида. Унифицируется их описание и навигация.

## 6. Содержание остальных документов

### setup.md — подготовка и настройки

Единый порядок разделов:

1. Проверенная среда и требования: версии, ОС, CPU, ресурсы; неизмеренные ресурсы так и обозначить.
2. Первичная подготовка: зависимости, загрузка артефактов, migrations, seed; для каждого сервиса только фактически нужные шаги.
3. Настройки: таблица переменных, создание локального окружения, расположение секретов.
4. Запуск: основной проверенный способ; альтернативный отдельно с его статусом проверки.
5. Проверка готовности: команды, ожидаемые коды, ограничения healthcheck.
6. Сеть и автономный режим: что скачивается при подготовке, что обращается в сеть во время работы, какие вызовы платные.
7. Типичные ошибки: симптом → причина → действие.

### architecture.md — устройство реализации

1. Компоненты и схема потока запроса.
2. Алгоритм обработки, правила и fallback.
3. Хранение и модель данных: источник истины, производные индексы/кеши, сохранность после restart.
4. Версионирование: модели, данные, каталог, промпты, API и привязка ответа к ним.
5. Параллельность и лимиты.
6. Внешние зависимости и границы доверия.
7. Связь с общей архитектурой и известные расхождения.

Скоринг: признаки → model bundle → сохранение inference; policy backend показывается отдельным участником. Feed: типизированный профиль → E5 → бонусы → диверсификация; реакции хранятся у backend. Ассистент: сессия → агент → инструменты; отдельно публикация знаний и состояния версий.

### integration.md — передача backend/frontend

1. Статус интеграции и ответственность сервисов.
2. Адреса, авторизация и управление идентификаторами.
3. Источники контрактов: нормативный OpenAPI, runtime OpenAPI, реализованный профиль, расхождения.
4. Последовательность вызовов: минимальный успешный сценарий.
5. Запросы и ответы: ссылки на исполняемые примеры; семантика полей, единиц и null.
6. Ошибки, timeout, retry, идемпотентность и fallback.
7. Совместимость версий и digests.
8. Обязанности backend и frontend.
9. Сквозные сценарии приёмки.

Таблица контракта: `операция | вход | выход | авторизация | ошибки | пример`. Не перепечатывать весь JSON OpenAPI в Markdown. Если runtime отличается от общего контракта, описывать разницу и требуемый адаптер явно.

### model-card.md — модели и качество

1. Назначение модели и допустимое использование результата.
2. Активные компоненты: модель, версия/revision, источник, лицензия, путь/manifest, preprocessing.
3. Данные и протокол обучения либо способ использования без обучения.
4. Метод оценки: метрики, наборы, разделение выборок, baseline и критерий выпуска.
5. Результаты со ссылками на точные отчёты.
6. Ограничения и непроверенные свойства.
7. Обновление, совместимость и откат — ссылка на operations.

Для скоринга различать активный CatBoost и неактивированный кандидат; JSON-параметры baseline оставить в артефакте и дополнить нормальным человекочитаемым описанием. Для feed описать E5 и правила отдельно; similarity не называть вероятностью полезности. Для ассистента отдельно перечислить E5, tokenizer и внешнюю LLM; оценка retrieval не является оценкой ответов генератора.

### data.md — данные и происхождение

1. Реестр наборов/корпусов/каталогов и их назначение.
2. Происхождение, лицензии и допустимое использование.
3. Схема и подготовка данных.
4. Разделение train/validation/test либо корпус и evaluation-сценарии; неприменимые части обозначить.
5. Версионирование, hashes и обновление.
6. Синтетические данные, персональные данные и ограничения выводов.

Скоринг ссылается на существующий DATASET_README, feed — на каталог и review, ассистент — на corpus manifest и правила подтверждения веб-снимков. Не дублировать редактируемые manifests в таблицах вручную.

### operations.md — обслуживание

1. Start/stop и проверка готовности.
2. Сохраняемое и временное состояние.
3. Обновление модели/каталога/корпуса/промпта.
4. Миграции и восстановление индексов.
5. Переключение выпуска и откат.
6. Логи и диагностика.
7. Backup/restore/reset: фактические команды, условия и какие данные изменяются. Если процедура не проверена — так и написать.

Не переносить команды между сервисами механически: у риска есть activate bundle, у feed подготовка комплекта, у ассистента публикация/отзыв версий и reindex.

### verification.md — фактически выполненные проверки

```markdown
# Проверки <название сервиса>

Снимок кода: <commit>. Дата: <ISO-8601 с timezone>.
Среда: <ОС/CPU/версии>. Исполнитель: <имя или роль>.

## Результаты
| Проверка | Команда / протокол | Результат | Доказательство | Ограничение |
|---|---|---|---|---|
| <unit tests> | <точная команда> | PASS / FAIL / SKIPPED / NOT_EXECUTED | <ссылка> | <что не покрыто> |

## Качество модели
<Метрика, набор, размер, версия модели, ссылка на отчёт и предел вывода.>

## Невыполненные проверки
<Что осталось и почему.>

## Воспроизведение
<Команды, зависимости, сеть/стоимость и ожидаемый результат.>
```

Одно место содержит актуальную сводку; JSON/XML и исторические аудиты остаются по прежним путям. Новый прогон не заменяется ссылкой на старый PASS. Для ассистента отдельно показать факт проверки retrieval и факт проверки настоящей LLM.

### THIRD_PARTY_NOTICES.md и CHANGELOG.md

Сторонние компоненты: `компонент | версия/revision | источник | лицензия/условия | роль | способ получения`. Отдельно отметить внешние API и собственные синтетические материалы. Условия использования платного API не называть лицензией открытых весов.

История изменений: дата, версия/commit, изменение поведения или контракта, требуемые действия интегратора, ссылка на evidence. Не переносить полный журнал Git.

## 8. Факты, которые должны сохраниться после унификации

| Свойство | Скоринг | Feed | Ассистент |
|---|---|---|---|
| Порт локального сервиса | 8001 | 8002 | 8000 |
| Авторизация | Bearer служебного токена | `X-Service-Token` | Bearer токена сессии; `X-Admin-Key` для admin |
| Хранение | PostgreSQL snapshots/inferences | Пользовательское хранилище вне ML | SQLite + Qdrant; сессии в памяти |
| Модельный runtime | Локальный CatBoost baseline | Локальная E5 | Локальная E5, внешняя платная LLM |
