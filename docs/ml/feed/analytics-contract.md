# Контракт экспорта событий ленты v1

Это дополнение к действующему API, не новый публичный endpoint. Схема: `ml/feed/analytics.schema.json`. Пример трёх записей: `ml/feed/examples/analytics-export.json`.

Backend экспортирует три таблицы Parquet с полями схемы либо эквивалентные JSON-записи. `requestJson` — сериализованный существующий FEED RankingRequest; его дополнительно проверяют runtime-схемой. В каждой таблице обязательны `subjectId`, `companyId`, `sessionId`, `exposureId`, `split`, `isSynthetic`. Для реального экспорта `isSynthetic=false`, `split=live`; генератор и обучающий адаптер этой поставки принимают только синтетические данные. Подключение real-data adapter требует отдельной проверки происхождения и правил разбиения.

| Таблица | Обязательное содержание |
|---|---|
| requests | Снимок RankingRequest до выдачи, requestedAt, policy, releaseId, experimentId/variant (пустая строка до экспериментов), randomizationUnit |
| issued | itemId, position 1–6, cardVersion, issuedAt; только карточки фактически отправленной порции |
| events | clientEventId, itemId, action, occurredAt, acceptedAt, acceptedOrder, visibleFraction, visibleMs |

`requestJson` содержит профиль, предыдущие topicReactions, полный eligible candidate set, requestId и версию/digest каталога. Полный порядок восстанавливается из ранжирования только при его сохранении; для текущего обучения достаточно полного candidate set и упорядоченной фактической порции. Если нужен аудит полной перестановки, храните RankingResult рядом со снимком запроса в собственном backend-хранилище. Нельзя заменять порядок выданной порции результатом повторного ранжирования позднее.

Идентификаторы непрозрачные: без ИНН, названий, телефона, почты и финансовых реквизитов. Request/exposure идентификаторы создаёт backend. Права на компанию и соответствие exposure проверяет backend. Сервис ML не хранит пользователей или события.

Последовательность: прочитать состояние → сформировать запрос → ранжировать → атомарно сохранить exposure и выданную порцию → отправить пользователю. Только после подтверждённой видимости возникает VIEW. Повтор cursor возвращает прежний exposure и не создаёт новую выдачу. Если скрытая карточка исключена при повторе, храните оригинал порции и отдельный факт доставки/скрытия; не переписывайте историю exposure.

При VIEW видимая доля ≥0,5 и непрерывная длительность ≥1000 мс. Для других событий поля видимости равны нулю. Это сигнал видимости, а не доказательство чтения. CLICK, HELPFUL и NOT_INTERESTED сохраняются отдельно. SAVE и READ_COMPLETE в v1 не вводятся: HELPFUL уже задаёт список полезного.

Уникальность clientEventId — в user/company. Точный повтор принимается без нового эффекта; повтор с иным содержимым даёт конфликт. В экспорт принятых событий дубли не попадают. `acceptedOrder` строго увеличивается внутри user/company и определяет последнее состояние реакции. Клиентское occurredAt не должно перезаписывать более новое серверное состояние. Серверные timestamps и порядок нужны для point-in-time признаков; генератор использует согласованные вымышленные часы.

`validate-data` проверяет каждую запись трёх таблиц по схеме до воспроизведения истории. Некорректные диапазоны видимости, недостающие и дополнительные поля отклоняются. Одинаковые `clientEventId` разных user/company допустимы; повтор внутри одного контекста отклоняется. Для VIEW схема требует долю 0,5–1 и длительность ≥1000 мс, для остальных действий — нулевые поля видимости.

HELPFUL/NOT_INTERESTED заменяют друг друга для карточки. Агрегаты считаются по последним реакциям карточек, не по числу нажатий. VIEW и скрытие сохраняются между посещениями; issued без VIEW исключает карточку только внутри текущей подборки. Реакция относится к карточке, действительно выданной в данном user/company/exposure, а не к любому кандидату ML.

Начальная label policy: последняя явная реакция в сессии имеет приоритет, затем CLICK. Снимок признаков остаётся состоянием ДО выдачи. Не добавляйте итоговую реакцию в тот же снимок. Непоказанные и неотреагировавшие карточки нельзя автоматически размечать отрицательными.

Перед первым реальным обучением потребуются real-data adapter, сроки завершения окна меток, правила разделения пользователей/компаний, исключение служебного трафика и проверка полноты доставки. Синтетические и реальные данные нельзя объединять без явной маркировки и отдельной оценки.
