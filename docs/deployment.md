# Развёртывание кредитного кабинета

Единственная основная конфигурация — корневой `compose.yaml`. Compose-файлы внутри ML-компонентов нужны для их самостоятельной разработки. Не запускайте их одновременно с основным стеком на тех же портах.

## Подготовка

Нужны Docker Engine / Desktop с Linux containers, Compose v2.20+ с BuildKit, Python 3.10+. Сборка не требует Node, Maven, Java или CUDA на хосте. На Windows используйте `python`, на Linux/macOS — `python3`, если так называется интерпретатор.

Рекомендуемые ресурсы, выделенные **Docker**, а не всему компьютеру:

| Режим | Назначение | Ориентир RAM |
|---|---|---|
| `core` | Кабинет, PostgreSQL, Risk, E5 Feed, ClamAV; ручное заполнение финансов | от 8 GB |
| `full` | Всё перечисленное + OCR, ассистент, Qdrant, поиск; внешний LLM | от 12 GB |
| `local` | Full с подключением к Ollama на хосте | full + память локальной модели |

Первая установка скачивает образы, зависимости и модели. Подготовьте от 30 GB свободного места с дополнительным запасом под кеш сборки. На CPU всё работает без обязательного GPU, но первая подготовка моделей и локальная генерация могут быть медленными. На маломощной машине используйте core; он всё ещё содержит E5 и ClamAV и не является режимом для 2 GB RAM.

Проверенный здесь вариант — Linux/amd64 внутри Docker Desktop на Windows. ARM64, старые CPU без требуемых ML-библиотеками инструкций и разные GPU пока не прошли полноценную приёмку. Принудительный `platform: linux/amd64` не установлен: скрытая эмуляция не должна создавать иллюзию нативной поддержки. Универсальная работа на любом оборудовании не обещается.

```sh
python scripts/deploy.py init
python scripts/deploy.py doctor
python scripts/deploy.py up --mode core
```

Откройте http://127.0.0.1:8080. Для full заполните в `.env` параметры LLM и запустите:

```sh
python scripts/deploy.py up --mode full
```

Пустой ключ не заменяется моками: OCR и ассистент сообщают о неготовности, и ожидание full завершается ошибкой. Core не требует LLM. Переход full → core не останавливает ранее запущенные дополнительные сервисы: при необходимости сначала выполните `down` с тем же именем проекта, затем `up --mode core`.

`init` добавляет только отсутствующие параметры и не меняет существующие значения. Если вы скопировали `.env.example` вручную и оставили пустые внутренние пароли, заполните их перед запуском. Нельзя менять пароль уже созданной БД только в `.env`: сначала измените его в PostgreSQL. `.env` не предназначен для Git. Режим 0600 применяется при создании на Unix; на Windows доступ определяется ACL пользователя.

## Повторный запуск и данные

```sh
python scripts/deploy.py status
python scripts/deploy.py logs
python scripts/deploy.py up --no-build
python scripts/deploy.py down
```

`down` сохраняет тома. `up` пересобирает только изменившиеся слои, ждёт готовности сервисов до 20 минут и показывает ошибку при неготовности. Подготовительные задания `feed-init`, `assistant-init`, `ml-migrate` завершаются с кодом 0 — это нормальное состояние. Долгоживущие сервисы перезапускаются после рестарта Docker. Логи ограничены тремя файлами по 10 MB на сервис.

Сборка по умолчанию идёт по одному уникальному образу, включая зависимости core: это уменьшает пик RAM даже при включённом Docker Bake. На мощной машине можно разрешить параллельную сборку через `--parallel 3`; фактический параллелизм Bake определяет сам. Maven/npm/pip используют BuildKit-кеши. Обрывы установки pip повторяются; подготовка моделей повторяется до трёх попыток, проверка контрольных сумм остаётся обязательной. Длительная недоступность реестров или Hugging Face всё равно требует восстановления сети.

Окончания строк shell-скриптов и SQL нормализуются при сборке. Скрипты PostgreSQL и миграции включены в образ, а не исполняются из Windows bind-mount. Исходники ML приводятся к LF перед проверкой закреплённых хешей; бинарные модели не переписываются и проверки не отключаются. Для старой Windows-БД мигратор принимает прежний checksum только если он точно совпадает с CRLF-вариантом той же SQL-миграции, затем сохраняет канонический LF-checksum. Содержательные изменения уже применённого SQL по-прежнему блокируются.

Имена томов зависят от имени Compose-проекта. Для существующей установки сохраняйте **то же имя** во всех командах:

```sh
python scripts/deploy.py up --project credit-audit-lf --context desktop-linux
python scripts/deploy.py status --project credit-audit-lf --context desktop-linux
```

Здесь `credit-audit-lf` — имя текущей локальной установки с вашими заявками; стандартное имя новой установки — `credit-integrated-mvp`. Смена имени создаст отдельные тома, а не перенесёт данные. Не выполняйте `docker compose down -v`, если данные нужны. Для переноса на другую машину нужны резервные копии PostgreSQL, файлов документов и остальных постоянных томов; перенос одного `.env` недостаточен. Порт 8080 должен быть свободен.

Можно закрепить имя один раз в `.env` через `COMPOSE_PROJECT_NAME`; в текущей локальной установке оно уже закреплено как `credit-audit-lf`. Тогда `--project` в обычных командах не нужен. При настройке старой установки сначала проверьте это значение, особенно если раньше задавали `-p` вручную.

## Локальная LLM без внешнего провайдера

Модель можно запускать на своём компьютере через [Ollama](https://docs.ollama.com/api/openai-compatibility). Внешний API-ключ, облачная отправка документов и оплата провайдеру не нужны. Между контейнерами и Ollama остаётся локальный HTTP-интерфейс `/v1`: это способ взаимодействия программ, а не облачный сервис. Tesseract, E5 и Risk уже выполняются локально.

1. Установите Ollama на хост. Для Apple Silicon это позволяет использовать ускорение хоста, не требуя GPU внутри Linux Docker.
2. Скачайте модель: `ollama pull qwen2.5:7b`. Это начальный вариант для проверки, не гарантия качества извлечения финансов и вызовов инструментов. Для меньших/больших моделей задайте `LOCAL_LLM_MODEL` в `.env`.
3. Разрешите доступ к Ollama из контейнеров. По умолчанию она слушает loopback: настройте `OLLAMA_HOST=0.0.0.0:11434`, перезапустите Ollama и ограничьте доступ к порту межсетевым экраном вашей машины. Не публикуйте незащищённую Ollama в интернет. Настройка для каждой ОС описана в [официальной FAQ](https://docs.ollama.com/faq).
4. Для запросов приложения настройте контекст Ollama, например `OLLAMA_CONTEXT_LENGTH=16384`, до запуска сервера. Больший контекст требует больше памяти. Локальный OCR по умолчанию ограничен 4096 выходными токенами и 24000 символами общего входа вместе со схемой: это начальные лимиты для небольших синтетических документов. Для длинных документов согласованно увеличивайте контекст модели, `LOCAL_OCR_MAX_TOKENS` и `LOCAL_OCR_MAX_CONTEXT_CHARS` в `.env`; превышение лимита приводит к явной ошибке, а не к молчаливому обрезанию. Контекст ассистента оценивается его закреплённым токенизатором, поэтому смена модели требует проверки реального расхода токенов.
5. Запустите `python scripts/deploy.py up --mode local`. Для текущей установки добавьте `--project credit-audit-lf --context desktop-linux`.

Overlay `deploy/compose.local-llm.yaml` подключает оба сервиса к `http://host.docker.internal:11434/v1`, задаёт техническое значение `ollama` вместо внешнего ключа и отключает специфические параметры внешнего провайдера. Основной `.env` и внешний ключ сохраняются; для возврата достаточно `up --mode full` с тем же проектом.

Для проверки доступности модели из контейнера:

```sh
docker compose -f compose.yaml -f deploy/compose.local-llm.yaml exec assistant python -c "import urllib.request; print(urllib.request.urlopen('http://host.docker.internal:11434/v1/models', timeout=10).status)"
```

Если ваш проект называется иначе, добавьте к `docker compose` `-p ИМЯ`. Ответ 200 доказывает доступность сервера, но не качественную генерацию: отдельно проверьте вопрос ассистенту и OCR синтетического документа. Локальная модель должна поддерживать JSON-ответы и вызовы инструментов. На слабом CPU возможен выход за существующий бюджет времени ассистента, даже если модель загрузилась. Флаг ready сейчас проверяет конфигурацию ключа и зависимости, а не успешную генерацию каждой моделью. Локальную генерацию в рамках этой проверки не запускали и модель Ollama автоматически не скачивали.

## Диагностика

`doctor` проверяет Docker/Compose и синтаксис конфигурации, показывает выделенные ресурсы. Это не полная проверка всех платформ и доступности внешних реестров. При ошибке `up` смотрите `status` и `logs`: нехватка RAM обычно проявляется как exit 137/OOM; недоступность сети — на этапе загрузки образов, пакетов или моделей. Проверка checksum не должна обходиться удалением проверок или пересчётом манифеста. Для прикладной проверки после запуска используйте `python scripts/integration/smoke.py --output reports/deploy-smoke.json`.
