# Вход и чистые кабинеты

Откройте `http://127.0.0.1:8080/login`. Вход выполняется по логину и паролю, выбор демопрофиля удалён. Аккаунт `company-a` открывает компанию А, `company-b` — компанию Б. Доступ к чужой компании закрыт на сервере.

## Данные для передачи проекта

Выполните `python scripts/deploy.py init`. Команда создаёт недостающие `CABINET_A_PASSWORD` и `CABINET_B_PASSWORD` в `.env` и отдельный файл `.local/cabinet-access.md` с готовыми данными входа. Передайте этот файл получателю проекта отдельно. Локальные пароли не встроены в интерфейс и не включены в Git. Исключение — два явно согласованных публичных пароля онлайн-демо, перечисленных в корневом README. Повторный `init` сохраняет существующие пароли.

Для смены пароля измените соответствующее значение в `.env` и пересоздайте backend: `docker compose up -d --no-deps backend`. При старте сервер сохраняет новый солёный PBKDF2-SHA256 хеш и отзывает старые сессии аккаунта. Пароль должен содержать от 12 до 256 символов. Публичные демоаккаунты `company-a` и `company-b` не блокируются на 15 минут после неверных паролей. Правильный пароль принимается сразу, включая старую блокировку в БД; успешный вход очищает её. Другие учётные записи сохраняют блокировку после пяти ошибок. Gateway ограничивает частоту входа: 30 запросов/мин на сетевой адрес, burst 20. При превышении возвращает `429 AUTH_RATE_LIMITED`, `Retry-After: 2`; это короткое ограничение запросов, а не блокировка аккаунта. За одним прокси адрес может быть общим.

## Очистка компаний А и Б

Для осознанной подготовки пустых кабинетов выполните `python scripts/reset_cabinets.py`. Для другого имени проекта или Docker context используйте `--project ИМЯ` и `--context ИМЯ`.

Команда временно останавливает backend и OCR worker, создаёт закрытую резервную копию базы в `.local/backups/`, затем одной транзакцией удаляет заявки, финансовые формы и снимки, документы и задания, решения, предложения, историю диалогов, настройки и реакции ленты компаний А и Б. Сессии их представителей отзываются. Учётные записи, компании, каталог, модели и база публичных знаний сохраняются. Данные других компаний не очищаются. Состояние запуска сервисов восстанавливается после операции. Резервные копии и недоступные из кабинета файлы в файловом томе сохраняются.

Очистка не выполняется при обычном запуске или обновлении. После входа в интерфейсе не должно остаться прежних заявок, документов или переписки; обычная стартовая лента материалов доступна.

## API

`POST /api/v1/auth/login`, `Content-Type: application/json`, разрешённый `Origin`, тело `{"login":"company-a","password":"…"}`. Успех устанавливает cookie `credit_session` с `HttpOnly` и `SameSite=Strict` и возвращает серверную сессию. Ошибка учётных данных возвращает `401 INVALID_CREDENTIALS`; причина не раскрывает существование аккаунта. Запросы без пароля и старые `/demo/api/v1/accounts`, `/demo/api/v1/session` не дают войти. Остальные запросы используют прежние cookie, CSRF и контекст компании.

## Обновление работающего стенда

[Пошаговая инструкция обновления](update-runtime.md) учитывает новую одно-коммитную main, сохраняет локальные изменения в stash и пересобирает backend/gateway с исходной Compose-конфигурацией. Старые locked_until вручную удалять не нужно.
